# AWS IAM — AssumeRole with External ID (Confused Deputy Prevention)

## Purpose

When a third party needs access to your AWS resources via cross-account role assumption, the external ID mechanism prevents the Confused Deputy problem — a class of privilege escalation attack where a third-party service is manipulated into accessing a customer's resources without the customer's authorization.

## What the External ID Does

The external ID allows the party assuming a role to assert the specific circumstances under which they are operating. A role trust policy containing an external ID condition means:
- Only calls that include the correct external ID can assume the role.
- Even if an attacker knows the role ARN, they cannot assume the role without the external ID.

> "The primary function of the external ID is to address and prevent the confused deputy problem."

## When to Use External ID

Use an external ID when:
1. You are an AWS account owner configuring a role for a third party that accesses multiple AWS accounts. You ask the third party for an external ID to include when assuming your role, then check for it in the trust policy.
2. You are the third party assuming roles across many customers. Assign a unique external ID per customer and instruct customers to add it to their trust policy; always include the correct external ID in your `AssumeRole` calls.

The external ID is **not optional** in multi-tenant SaaS provider scenarios where a single third-party account accesses many customer accounts.

## The Confused Deputy Problem

Without an external ID:
- Customer A gives third-party service (Example Corp) access to customer A's account.
- An attacker could trick Example Corp into using its permissions to access Customer B's resources by providing Customer B's role ARN.
- Example Corp cannot distinguish whether it's acting on behalf of Customer B legitimately or being manipulated.

With an external ID:
- Customer B's trust policy requires `sts:ExternalId = "Customer-B-unique-ID"`.
- The attacker cannot supply this value because they don't know it.
- Example Corp checks that it has an on-file customer record with that external ID before making the call.

## Trust Policy Configuration

The external ID condition goes in the role's trust policy `Condition` block:

```json
{
  "Principal": { "AWS": "arn:aws:iam::EXAMPLE_CORP_ACCOUNT_ID:root" },
  "Condition": {
    "StringEquals": {
      "sts:ExternalId": "Unique ID Assigned by Example Corp"
    }
  }
}
```

The `Action` is `sts:AssumeRole`.

## AssumeRole API Call

The third party includes the ExternalId parameter:

```bash
aws sts assume-role \
  --role-arn arn:aws:iam::CUSTOMER_ACCOUNT:role/ROLE_NAME \
  --role-session-name SESSION_NAME \
  --external-id CUSTOMER_EXTERNAL_ID
```

If the external ID is absent or incorrect, the call fails with an authorization error.

## External ID Properties

- External ID is **not a secret**. After creating a secret (access key, password) in AWS, you cannot view it again. The external ID for a role can be seen by anyone with permission to view the role.
- External IDs are generated by the third party (Example Corp), not by customers, to ensure global uniqueness.
- Format constraints: minimum 2 characters, maximum 1,224 characters; alphanumeric without whitespace; permitted symbols: `+`, `=`, `,`, `.`, `@`, `:`, `/`, `-`.
- In a multi-tenant environment: one external ID per AWS account; should be a random string generated by the third party.

## Setup Process (Step by Step)

1. Third party (Example Corp) generates a unique external ID for each customer and provides: their AWS account ID + the external ID.
2. Customer creates an IAM role with:
   - Trust policy: principal = Example Corp's AWS account; condition: `sts:ExternalId` = the customer's external ID.
   - Permission policy: the specific actions Example Corp needs.
3. Customer provides role ARN to Example Corp.
4. Example Corp calls `sts:AssumeRole` with the role ARN and the customer's external ID.
5. If both match the trust policy, AssumeRole succeeds and returns temporary credentials.
6. Example Corp uses temporary credentials to access customer resources.

## Security Recommendation

> "When a customer gives you a role ARN, test whether you can assume the role both with and without the correct external ID. If you can assume the role without the correct external ID, don't store the customer's role ARN in your system."

This ensures customers have properly configured their trust policies before relying on the external ID protection.

## Temporary Credentials

AssumeRole returns temporary security credentials (access key ID, secret access key, session token) with a configurable duration. These are scoped to the permissions defined in the role's permission policy. This is the IAM best practice for third-party cross-account access — never share long-term credentials (IAM user access keys).
