# AWS STS AssumeRole with External ID

`sts:AssumeRole` with an External ID is the IAM mechanism for securely delegating cross-account AWS access in multi-tenant or third-party-provider scenarios. The External ID prevents the **Confused Deputy problem** — a privilege escalation attack where a legitimate service is manipulated into accessing one customer's resources while acting on behalf of another.

Source: [wiki/sources/aws-sts-assume-role-external-id.md]

---

## The Confused Deputy Problem

**Without external ID:**
- Third-party service (e.g., a centralized platform) has permission to assume roles in multiple customer AWS accounts.
- An attacker provides Customer B's role ARN to the service.
- The service, having no way to verify it's genuinely acting for Customer B, assumes the role — giving the attacker access to Customer B's resources.

**With external ID:**
- Customer B's trust policy requires `sts:ExternalId = "B-unique-ID"`.
- The third-party service only sends AssumeRole calls for Customer B when it has a legitimate Customer B record in its own system with that external ID.
- An attacker cannot construct the correct external ID → AssumeRole fails.

---

## Trust Policy Configuration

The external ID condition lives in the IAM role's **trust policy**:

```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::THIRD_PARTY_ACCOUNT_ID:root" },
  "Action": "sts:AssumeRole",
  "Condition": {
    "StringEquals": {
      "sts:ExternalId": "Customer-Unique-External-ID"
    }
  }
}
```

Without the `Condition` block, any principal in the third party's account can assume the role.

---

## AssumeRole API Call

The calling principal includes the `--external-id` parameter:

```bash
aws sts assume-role \
  --role-arn arn:aws:iam::CUSTOMER_ACCOUNT:role/ROLE_NAME \
  --role-session-name SESSION_NAME \
  --external-id CUSTOMER_EXTERNAL_ID
```

If `--external-id` is absent or the value does not match the trust policy condition, the call fails with an authorization error.

---

## External ID Properties

| Property | Value |
|----------|-------|
| Secrecy | NOT a secret — IAM describe-role permission reveals it |
| Generator | The third party (not the customer) — to ensure global uniqueness |
| Min length | 2 characters |
| Max length | 1,224 characters |
| Allowed characters | Alphanumeric; `+`, `=`, `,`, `.`, `@`, `:`, `/`, `-` |
| Recommended value | Random string generated by the third party per customer |

---

## When to Use External ID

| Scenario | Use external ID? |
|----------|-----------------|
| Third party accesses a single customer account | Optional — reduced attack surface |
| Third party accesses multiple customer accounts (multi-tenant) | **Required** — prevents confused deputy |
| Intra-organization cross-account (same company, same AWS Org) | Optional — lower risk, but still best practice |
| AWS service (S3, Lambda, etc.) as principal | Use `aws:SourceAccount` / `aws:SourceArn` instead |

---

## AssumeRole Response

On success, `sts:AssumeRole` returns **temporary security credentials**:

- `AccessKeyId`
- `SecretAccessKey`
- `SessionToken`
- `Expiration` (ISO 8601)

These are scoped to the permissions defined in the assumed role's **permission policy**, not the trust policy.

---

## Security Recommendations

- Always test AssumeRole both with and without the correct external ID. If it succeeds without it, do not onboard that customer's role ARN — require them to add the `sts:ExternalId` condition first.
- Never share long-term IAM user access keys for cross-account access. Use roles and temporary credentials only.
- Enable IAM Access Analyzer to identify roles accessible outside your zone of trust.

## Relationship to Platform MCP Server (Decision 0015)

The Platform MCP Server is the centralized service acting across multiple LINQ AWS accounts (one per product). This entity is directly applicable:

- The Platform MCP Server = "third party" in the external ID model.
- Each LINQ product AWS account = "customer account" that creates an IAM role for the Platform MCP Server.
- Each product account's trust policy includes `sts:ExternalId = "<product-account-specific-ID>"`.
- The Platform MCP Server maintains a mapping of product → external ID and includes it in AssumeRole calls.

Open questions:
- Is this multi-tenant enough to require external IDs (LINQ internal org vs. true third-party)?
- Who generates and stores the external IDs for each LINQ product account?
- What session duration is appropriate for Platform MCP Server role assumption?
