# Decision 0015 — Centralized Platform MCP Server with cross-account dispatch

**Status:** Proposed (2026-05-04). Backed by the architecture review in [`docs/research/0015-centralized-platform-mcp/`](../research/0015-centralized-platform-mcp/00-overview.md).

## Context

LINQ runs each product in a dedicated AWS account; a shared **Platform Services** AWS account hosts cross-cutting capabilities `[ASSUMED]`. Internal AI agents — Claude Code, internal dev tools, and ops dashboards — increasingly need read access to product data, application logs, and internal APIs. The default of one MCP server per product creates sprawl in identity, authorization, governance, AI context scope, and operational ownership; a single centralized broker is the alternative.

V1 scope is locked by the stakeholder brief: internal agents only, **read-only**, 4 products with 40–200 handlers (planning for 5–10× growth over 3 years), Auth0 for both human SSO and agent (M2M) identity, no formal compliance certification.

A five-role architecture review (architecture, MCP/AI, Security & IAM, Platform, Cost & Reliability) validated the proposed design, found it structurally sound, and required specific refinements before lock-in. The review's source role memos live at [`docs/research/0015-centralized-platform-mcp/role-passes/`](../research/0015-centralized-platform-mcp/role-passes/) and the synthesis lives in the research folder above.

Slot 0014 is reserved by [Decision 0013](0013-karpathy-wiki-pattern.md) for the canonical LINQ product-slug list. This work claims slot **0015**.

## Decision

Adopt a single, platform-owned MCP server in the Platform Services account as the **only** internal-AI entry point to LINQ product data and capabilities, brokering cross-account invocations of product-owned handlers via a versioned handler registry. The pattern is **"Auth0-fronted MCP broker with cross-account credential exchange"** — distinct from, and coexisting with, the per-user OAuth pattern of [Decision 0008](0008-mcp-connectors.md).

Specific binding choices:

- **Transport.** HTTP/SSE, conforming to the [MCP 2025-06-18 authorization spec](../../knowledge/wiki/entities/mcp-authorization.md). STDIO rejected — incompatible with multi-tenant brokering. Failure mode: STDIO would bypass the entire OAuth 2.1 / RFC 9728 / RFC 8707 layer and ship credentials via environment variables, which does not work for a server brokering 4+ products.
- **Tool catalog.** Per-product prefix namespace (`erp.*`, `crm.*`) from day one. Server-side `tools/list` projection by authenticated principal (`sub` / `client_id`) so no agent receives the full catalog. Failure mode this prevents: catalog injection of ~50–100k tokens at 200 handlers, ~500k–1M at 2000.
- **Identity.** Agents authenticate to the MCP server via Auth0 M2M (client credentials grant, [Auth0 M2M entity](../../knowledge/wiki/entities/auth0-m2m.md)). The MCP server validates `iss`, `aud`, signature, and `kid`. The MCP server self-hosts `/.well-known/oauth-protected-resource` ([RFC 9728](../../knowledge/wiki/entities/mcp-authorization.md)) — independent of whether Auth0 supports RFC 9728. **One Auth0 M2M application per service-identity class** (3–5 total in v1); per-handler M2M apps are forbidden by platform contract.
- **End-user identity propagation (OBO).** RFC 8693 token exchange ([token-exchange entity](../../knowledge/wiki/entities/oauth-token-exchange.md)) is the contract; the wire shape is `subject_token = user JWT, actor_token = agent JWT, audience = product handler`, output JWT carries `sub = user_sub`, `act.sub = agent_client_id`, TTL ≤ 5 min. If Auth0 supports RFC 8693, the broker is a thin proxy. If not — Phase A could not verify — v1 implements the broker as an Auth0 Action or a Platform-owned signer (KMS asymmetric key) with the same on-the-wire shape, swappable later. Token passthrough to downstream APIs is forbidden by the MCP spec and by platform contract.
- **Authorization split.** Coarse-grained at the MCP server: `(agent_client_id, user_sub, tool_id)` resolved against the registry; agent must hold `requiredScopes[]`, user must hold `requiredPermissions[]`. Fine-grained at the handler: tenant + record. The registry **rejects** any handler entry missing a `tenantSourceClaim` field at registration. Tenant ID is read from the user's verified token by the MCP server and injected as a separate, signed argument; the agent cannot supply tenant directly.
- **Cross-account invocation.** `sts:AssumeRole` with **per-product External ID** as the default mechanism for all three handler substrates ([STS + External ID entity](../../knowledge/wiki/entities/sts-assume-role-external-id.md)). Layer `aws:PrincipalOrgID`-conditioned trust policies and SCP guardrails as additional defense, not as substitute. External IDs are identifiers, not credentials — generated per-product by the platform at onboarding, stored in the registry's product table, surfaced for inclusion in product trust policies. Failure mode this protects against: Confused Deputy across products under registry tampering, tool-ID mis-resolution, or future product spin-out into a separate AWS Org. Lambda resource-based policies ([entity](../../knowledge/wiki/entities/lambda-resource-policy.md)) remain a documented narrow-case alternative for invoke-only handlers, never the default.
- **Registry.** Single DynamoDB table, on-demand billing, partition key `pk = TOOL#<id>`, sort key `sk = VERSION#<semver>` with parallel `LABEL#stable|beta` items for atomic relabel-based rollback. Three GSIs: `status`, `owner`, `productAccount`. Schemas externalized to S3 (sidesteps DynamoDB item-size limits and gives a free audit trail). Streams enabled to drive `notifications/tools/list_changed` and the registry-write audit log. Schema language: **JSON Schema** (matches MCP spec).
- **Handler abstraction.** `handlerType` is **invisible to the agent**. The MCP server calls a single internal `invoke(arn, scopes, input) → output`; an adapter layer dispatches per substrate (Lambda Invoke, ECS RunTask + result polling, Step Functions StartSyncExecution). Agents see one tool with one schema regardless of substrate. Per-handler `timeoutMs` and `expectedLatencyP50Ms` in the registry, surfaced in the MCP `description`, give agents enough planning information without leaking substrate.
- **v1 read-only enforceability.** Every registered tool declares `sideEffects: "read" | "write"`. The MCP server **refuses** to register entries with `sideEffects: "write"` in v1. A separate URL prefix or endpoint is reserved for mutating tools when v2 lands so audit, rate-limiting, idempotency, and human-in-the-loop middleware can attach there without touching read paths.
- **v2 forward-compat.** Reserve `idempotencyKey` in the input envelope today (v1 reads ignore it). Reserve mutation error classes (`IDEMPOTENCY_CONFLICT`, `PRECONDITION_FAILED`, `PARTIAL_SUCCESS`) in the error envelope enum today (v1 handlers must not emit them). These are one-line additions now and breaking changes later.
- **Federation escape hatch.** Reserve `handlerType: "remote-mcp"` in the registry — a handler entry whose target is a product-owned MCP server URL the platform proxies to. Activated by Phase B gate when handler count exceeds 800 OR when ≥ 2 product teams are review-bottlenecked at the platform write path. Costs ~1 week of design now; converts a future federation migration into a feature flag.
- **Caching.** Layered: 5-min in-process registry cache, 15-min ElastiCache shared cache, 1-h STS session cache (50-min effective with 10-min refresh margin), 23-h Auth0 M2M token cache, per-handler result cache via registry-declared `cacheTtlSeconds`.
- **Compute.** Lambda + API Gateway HTTP API for the MCP server in v1, single-region multi-AZ. Provisioned concurrency = 2 only if measured P95 > 1500 ms for 7 consecutive days. Multi-region deferred until any non-internal user is onboarded or Platform Services availability target moves from 99.5% to 99.9%.
- **SLOs.** v1 internal-only: availability 99.5%, P95 1500 ms. v2 (any external exposure): availability 99.9%, P95 800 ms.
- **Audit.** Single per-request JSON record covering agent → user → tool → handler → tenant → outcome → latency, written from the MCP server to a Platform-Services-account log group with S3 Object Lock retention (1 year v1, 7 year before any compliance scope). `request_id` embedded in `RoleSessionName` and STS session tags correlates platform audit to per-product CloudTrail.
- **Onboarding.** Policy-as-code on the registry write path. A product-team PR ships through CI checks (schema validation, scope spelling, account-allowlist match, owner team in directory). Platform-team review is required only at boundary expansions: new product account, new handler substrate, new `requiredScopes` value. A product team adding their 50th handler hits zero platform-team queues.

The rejected alternatives, in brief: (a) federated MCP servers per product with shared identity broker — quadruples implementation work and gives weak governance for v1; (b) API Gateway / EventBridge with MCP as thin adapter — viable if LINQ already has mature API Gateway, forces MCP semantics into a request/response shape that doesn't quite fit; (c) hybrid thin platform MCP delegating to product-owned MCP servers — preferred long-term destination, reachable incrementally via the `remote-mcp` `handlerType` escape hatch above. Full scoring: [`02-comparison-matrix.md`](../research/0015-centralized-platform-mcp/02-comparison-matrix.md).

## Consequences

- **Single point of governance.** All authorization, audit, rate limiting, and tool-catalog policy live at one seam. Adding a 5th product reuses the same primitives.
- **Single point of availability.** MCP-server outage stops all agent traffic. v1 mitigated by multi-AZ; v2 trigger forces multi-region.
- **Centralized blast radius for write ambition.** v1 read-only is enforceable architecturally via the `sideEffects` gate. Without it, v2 retrofits write semantics onto a server already in production with no test surface to prove read-only-ness held — this decision protects against that.
- **Coexists with [ADR 0008](0008-mcp-connectors.md), does not supersede it.** Atlassian MCP (and any future external-SaaS MCP) continues to use per-user OAuth via dedicated MCP servers. The Platform MCP Server applies only to **internal LINQ product data**. Per-product onboarding records which pattern applies.
- **Sub-linear cost in handler count holds — conditionally.** The "sub-linear" claim is true if and only if (1) Auth0 M2M apps are shared across handlers (one per service-identity class), (2) IAM roles are shared per product with handler-name-conditioned policies, and (3) dashboards are templated with handler as a CloudWatch dimension. Without these, fixed cost grows linearly with handler count and the 3-year target becomes a multi-thousand-dollar/month line. Platform contract enforces all three.
- **Auth0 dependencies that must close before Accepted status.** Three Phase A gaps remain unverified: (1) Auth0 RFC 9728 support — closed by self-hosting the metadata document on the MCP server, no Auth0 dependency; (2) Auth0 RFC 8693 native support — open, fallback path is Auth0 Action / KMS signer with identical wire shape; (3) AssumeRoleWithWebIdentity setup for LINQ topology — v1 uses standard `AssumeRole` instead, since the MCP server has its own Platform Services AWS principal. None of these block v1; all three are recorded with named fallbacks.
- **`handlerType: "remote-mcp"` is an explicit Phase B gate.** Documented now; activated only when handler count or team count crosses the stated threshold. Platform team owns the gate metric and the activation review.
- **On-call boundaries.** Auth, registry, dispatch, and transport faults page Platform. Handler logic, IAM trust-policy misconfiguration, and downstream-resource faults page the owning product team. STS AssumeRole fault: Platform owns until proven product-side IAM is mis-set, then product. Documented in [`01-architecture.md`](../research/0015-centralized-platform-mcp/01-architecture.md).

### Phase-1 POC

Scope and acceptance criteria: [`04-phase-1-poc.md`](../research/0015-centralized-platform-mcp/04-phase-1-poc.md). One product, one handler (`<product>.<read-handler>`), one agent (Claude Code internal). End-to-end: agent → MCP server → Auth0 M2M validation → registry lookup → token exchange → STS AssumeRole → handler invoke → audit record landed. POC succeeds when audit log shows the full agent → user → tool → handler → tenant → outcome chain for a real read against a real tenant.

### Open questions

Stakeholder decision log: [`05-open-questions.md`](../research/0015-centralized-platform-mcp/05-open-questions.md). Each question carries the guess we'd make if forced to decide today. The questions that block Accepted status are: Auth0 RFC 8693 native support; LINQ Auth0 enterprise tier and M2M entitlement; whether all 4 product accounts share one AWS Organization; existence of a centralized logging account.
