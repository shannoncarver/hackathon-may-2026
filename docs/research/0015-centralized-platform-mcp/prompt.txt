# Research Brief: Centralized Platform MCP Server for Multi-Account AWS

## Mission

You are an architecture review team tasked with evaluating, stress-testing, and refining a proposed design for a **centralized, platform-owned MCP (Model Context Protocol) server** that brokers all AI agent access to company data and capabilities across a multi-account AWS estate. Your output will inform a go/no-go decision and, if green-lit, a phase-1 implementation plan.

The proposal is described below in the "Proposed Architecture" section. Treat it as a hypothesis, not a foregone conclusion.

---

## Team Composition & Roles

Operate as a cross-functional team. Each role brings a distinct lens; the Lead Solutions Architect owns synthesis and the final recommendation. Surface disagreement explicitly rather than smoothing it over.

- **Lead Solutions Architect** — End-to-end design coherence, alternative-pattern comparison, final recommendation.
- **Security & IAM Engineer** — Cross-account trust, identity propagation (user → agent → MCP → handler), least-privilege scoping, secret/credential management, audit and governance.
- **MCP / AI Integration Specialist** — Protocol fit, tool/resource modeling, context scoping, agent ergonomics, latency and timeout behavior expected by MCP clients.
- **Platform Engineer** — Registry schema and lifecycle, handler abstraction (Lambda / ECS / Step Functions), routing logic, deployment and versioning.
- **Cost & Reliability Engineer** — Cost model under projected scale, blast radius, fault isolation, observability, SLOs.

---

## Background

The company operates a portfolio of products. Each product is deployed in its **own dedicated AWS account**; a shared **Platform Services AWS account** hosts cross-cutting capabilities. Product stacks are heterogeneous (Angular/.NET, Oracle, DynamoDB, Lambda, ECS, Step Functions, etc.).

AI agents — **Claude Code, internal developer tools, and ops dashboards** — increasingly need **read access** to product data, application logs, product APIs, and other operational signals. All agents in v1 scope are internal; no customer-facing exposure is planned for the initial rollout.

The default approach (one MCP server per product or per use case) creates sprawl: identity, authorization, governance, AI context scope, and operational ownership all become harder to manage as the number of MCP endpoints grows.

The existing identity provider for human users and tenant identity is **Auth0**, and Auth0 is also assumed for agent (machine-to-machine) identity.

---

## V1 Scope (Locked)

These constraints are decided. Do not re-litigate them; design within them and note any decision that would constrain future expansion.

- **Agents:** Internal only — Claude Code, internal dev tools, ops dashboards. No customer-facing exposure.
- **Operations:** **Read-only.** No mutating handlers in v1.
- **Scale:** 4 products, **10–50 handlers per product** (≈40–200 handlers total in v1). Plan for 5–10× growth over 3 years.
- **Identity:** **Auth0** for both human user authentication/authorization and agent (M2M) identity.
- **Compliance:** No formal certification scope (SOC 2 / HIPAA / PCI) in v1. Design should not foreclose adding it later.

---

## Proposed Architecture (Hypothesis Under Review)

A single, platform-owned MCP server — deployed in the Platform Services account — serves as the **only** AI-to-company-resource entry point.

### Components

1. **MCP Server** *(Platform Services account)* — Receives MCP requests from AI agents, authenticates the caller, applies authorization, resolves the request to a handler via the registry, invokes the handler cross-account, and returns the result.
2. **Handler Registry** *(DynamoDB, Platform Services account)* — Maps MCP tool/resource identifiers to handler metadata: target ARN (Lambda / ECS / Step Function), invocation method, the IAM role to assume for cross-account invocation, input/output schema, RBAC requirements, version, owner, etc.
3. **Handlers** *(Product AWS accounts)* — Lambda functions, ECS tasks, or Step Functions in the product account that actually fetch or mutate data. Each handler is owned by the product team that owns the underlying data.

### Reference Flow (from stakeholder)

> An AI agent asks the MCP server: *"Does user `[alice@example.com](mailto:alice@example.com)` have access to the ERP product for tenant `acme`?"*
>
> 1. MCP server authenticates the calling agent and resolves the requesting principal.
> 2. MCP server looks up the tool `erp.checkUserAccess` in the registry.
> 3. Registry returns handler metadata, e.g. `{ handlerType: "lambda", arn: "arn:aws:lambda:us-east-1:<erp-account>:function:erp-check-user-access", assumeRoleArn: "arn:aws:iam::<erp-account>:role/PlatformMcpInvoker", requiredScopes: [...] }`.
> 4. MCP server assumes the cross-account role, invokes the Lambda, and returns the response to the agent.

## Research Objectives

Produce a defensible answer to each:

1. **Is the proposed architecture sound?** Identify the strongest reasons it works and the strongest reasons it might fail, given AWS multi-account realities and the MCP specification.
2. **What are the failure modes?** Security, performance, reliability, governance, cost, developer experience.
3. **What alternatives should be compared?** At minimum:
   - (a) Federated MCP servers per product with a shared identity broker.
   - (b) API Gateway / EventBridge pattern fronting per-product handlers, with MCP as a thin adapter.
   - (c) Hybrid: a thin platform MCP server that delegates to product-owned MCP servers.
4. **What's the recommended path?** Either endorse the proposed design (with refinements), recommend an alternative, or propose a phased migration.

## Specific Areas to Investigate

For each area, produce: findings → risks → recommendation.

### MCP Protocol Fit
- Does a single MCP server with N handlers map cleanly to MCP's tool / resource / prompt primitives?
- Tool catalog structure: flat namespace vs. per-product prefixes vs. hierarchical resources.
- Dynamic tool discovery as handlers are added or removed.
- Context-window implications: avoid leaking the entire catalog into agent context.

### Identity & Authorization
- **Agent → MCP server authentication via Auth0** — most likely a Machine-to-Machine (client credentials) grant for the agent's service identity. Evaluate alternatives if this doesn't fit (e.g., signed JWTs from a trusted internal issuer).
- **End-user identity propagation** — how the human invoking the agent is represented in downstream handler calls. Token exchange, OAuth on-behalf-of, or signed assertions carrying the user's Auth0 `sub` claim. Recommend a concrete pattern.
- **Where authz decisions live**:
  - MCP server (coarse-grained): can this agent + this user reach this tool at all?
  - Handler (fine-grained): can this user read this tenant's specific row?
  - Recommend the split explicitly and define what each layer enforces.
- **Auth0 RBAC integration** — how product-defined roles/permissions surface to the registry and to handlers.
- **Multi-tenant scope enforcement** — handlers ultimately enforce tenant boundaries, but the platform should make it hard to get wrong (e.g., tenant ID required in every handler contract).

### Cross-Account Invocation
- `sts:AssumeRole` with external ID and session tags vs. resource-based policies on the target Lambda/ECS service.
- Credential caching and rotation.
- Network path: same-region invocation, VPC implications, PrivateLink if needed.
- Per-tenant or per-handler isolation strategies.

### Registry Design
- DynamoDB schema (partition/sort key choice, GSIs).
- Versioning, deprecation, and backward compatibility for handlers.
- Input/output schema validation (JSON Schema? Smithy? OpenAPI?).
- Self-service registration vs. platform-team-curated.
- Change audit and approval workflow.

### Handler Abstraction
- Common contract across Lambda, ECS, Step Functions.
- Sync vs. async handlers — most v1 reads should be sync; flag any read pattern that genuinely needs async (e.g., large log scans) and how it surfaces to an agent.
- Timeout and retry semantics. Reads are idempotent, so aggressive retry is safe — design for it.
- Error taxonomy and how errors surface in MCP responses.
- Forward-compatibility note: identify which contract decisions would need to change to support write/mutating handlers in v2.

### Observability & Governance
- What gets logged (request, principal, tenant, handler, latency, outcome) and where.
- Internal audit trail for "which agent/user accessed which data when." No formal compliance certification in v1, but structured logs should support adding it later.
- Rate limiting and quotas (per agent, per user, per tenant, per handler).
- Data classification — how handlers declare returned data sensitivity (PII, financial, etc.) so the platform can enforce policy as it matures.

### Cost & Scale
- Per-request cost model (MCP server + Lambda invocation + DynamoDB lookup + cross-account STS).
- Projected scale: ~40–200 handlers across 4 products in v1; plan for 5–10× growth over 3 years.
- Estimate requests/sec, agent concurrency, and tenant fan-out.
- Cold-start implications for Lambda handlers; warm-pool strategies if latency demands it.
- Caching strategy for read-heavy handlers and registry lookups (read-only v1 makes caching especially attractive).

### Operations & Developer Experience
- Onboarding workflow for a product team adding a new handler.
- Local testing story.
- Versioning and rollout (blue/green for handlers, feature flags in the registry).
- On-call ownership: platform team vs. product team boundaries when something fails.

## Evaluation Criteria

A successful proposal scores well on:

- **Security** — Least-privilege end-to-end; full auditability; tenant isolation.
- **Governance** — Single point of policy enforcement; clear ownership boundaries.
- **Scalability** — Handles a 10× increase in handler count without architectural change.
- **Operability** — Clear failure isolation; product teams ship handlers without a platform-team bottleneck.
- **Agent UX** — Acceptable latency; sensible tool catalog; useful error surfaces.
- **Cost** — Predictable; sub-linear in handler count.

## Out of Scope (for this research phase)

- **Write / mutating handlers** — v1 is read-only. Note any design choice that would later constrain write support, but do not design for writes.
- **Customer-facing agent exposure** — v1 agents are internal only (Claude Code, internal dev tools, ops dashboards).
- **Formal compliance certification** (SOC 2, HIPAA, PCI) — not in v1 scope; design should not foreclose adding it later.
- **Specific MCP server framework selection** (FastMCP vs. official SDK vs. custom) — note tradeoffs but don't pick.
- **Identity-provider vendor evaluation** — Auth0 is locked in for both human user authentication and agent (M2M) identity.
- **AWS pricing negotiation.**
